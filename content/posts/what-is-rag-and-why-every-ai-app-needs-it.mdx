Large language models are impressive until you ask them about something that happened last week, or something specific to your company, or a document they've never seen. They confidently give you an answer anyway. That's the problem RAG solves.

**RAG** stands for Retrieval-Augmented Generation. The idea is simple: before asking the model a question, fetch the relevant documents from your own knowledge base and include them in the prompt. The model then answers based on what you gave it, not just what it was trained on.

---

## Why LLMs alone aren't enough

Every LLM has a training cutoff. Claude, GPT-4, Gemini — they all stopped learning at some point. Ask them about a news story from last month and you'll get a hallucination or a refusal.

Beyond the cutoff problem, there's the scale problem. You can't fine-tune a model every time your product documentation changes. And you can't shove your entire knowledge base into the context window — that gets expensive and slow.

RAG solves both problems by keeping your knowledge outside the model and retrieving only what's relevant at query time.

## How RAG works

The pipeline has three stages:

### 1. Indexing (done once, offline)

You take your documents — PDFs, markdown files, database records, web pages — split them into chunks, convert each chunk into a vector embedding, and store those embeddings in a vector database.

```python
from openai import OpenAI
import numpy as np

client = OpenAI()

def embed(text: str) -> list[float]:
    response = client.embeddings.create(
        model="text-embedding-3-small",
        input=text
    )
    return response.data[0].embedding

# Split document into chunks and embed each one
documents = [
    "Our refund policy allows returns within 30 days.",
    "Premium subscribers get priority support.",
    "The API rate limit is 100 requests per minute.",
]

vectors = [(doc, embed(doc)) for doc in documents]
```

### 2. Retrieval (at query time)

When a user asks a question, you embed the question using the same model, then find the chunks whose vectors are closest to the question vector. "Closest" means semantically similar, not just keyword-matching.

```python
def cosine_similarity(a: list[float], b: list[float]) -> float:
    a, b = np.array(a), np.array(b)
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

def retrieve(query: str, top_k: int = 3) -> list[str]:
    query_vector = embed(query)
    scored = [
        (doc, cosine_similarity(query_vector, vec))
        for doc, vec in vectors
    ]
    scored.sort(key=lambda x: x[1], reverse=True)
    return [doc for doc, _ in scored[:top_k]]
```

### 3. Generation

You inject the retrieved chunks into your prompt and ask the model to answer based on them.

```python
def answer(question: str) -> str:
    context_docs = retrieve(question)
    context = "\n".join(f"- {doc}" for doc in context_docs)

    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[
            {
                "role": "system",
                "content": (
                    "Answer the user's question using only the context below. "
                    "If the answer isn't in the context, say so.\n\n"
                    f"Context:\n{context}"
                )
            },
            {"role": "user", "content": question}
        ]
    )
    return response.choices[0].message.content

print(answer("Can I get a refund after 30 days?"))
# → "Based on the provided context, refunds are allowed within 30 days,
#    so a refund after 30 days would not be covered by the policy."
```

## What to use in production

The example above uses a list and cosine similarity, which works for a few hundred documents. For anything larger, you need a proper vector database:

| Database | Best for |
|----------|----------|
| **Pinecone** | Managed, zero ops, fast |
| **Weaviate** | Open source, good filtering |
| **pgvector** | Already using Postgres |
| **Chroma** | Local development / prototyping |
| **Qdrant** | High performance, Rust-based |

For most new projects, start with **Chroma** locally and **Pinecone** in production. The API is similar enough that switching is straightforward.

## Common RAG mistakes

**Chunks that are too large.** If your chunks are 2,000 tokens each, the retrieved context is noisy and expensive. Aim for 200–400 tokens with some overlap between chunks.

**Not cleaning the source documents.** Headers, footers, page numbers, and HTML artifacts confuse the embedding model. Strip them before indexing.

**Forgetting metadata.** Store the source URL, document title, and section alongside each chunk. Use it to show citations in your UI — users trust answers more when they can verify the source.

**Using the wrong embedding model.** `text-embedding-3-small` is good enough for most use cases and cheap. Don't reach for `text-embedding-3-large` until you've measured that it actually improves your retrieval quality.

---

## When RAG isn't the answer

RAG works well when your knowledge base is mostly factual documents. It works poorly when:

- Your documents are highly structured tabular data → use SQL instead
- You need the model to reason across many documents simultaneously → fine-tuning or a larger context window is better
- Your data changes every few seconds → the indexing latency becomes a problem

RAG is a powerful default for knowledge-grounded AI apps. Start here, measure retrieval quality with a few test queries, and optimize from there.
